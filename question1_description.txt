Question 1: Computing a Neural-Network Layer on a Cluster
==========================================================

WHAT IT IS
----------
A neural network layer is a matrix multiplication: C = A x B.
- A holds the inputs (one example per row)
- B holds the weights (one neuron per column)
- C holds the outputs

We use square N x N matrices. For N = 32768, each matrix is 8 GiB, so
all three together (24 GiB) cannot fit on one machine. The work must be
split across multiple nodes using MPI, with OpenMP threads inside each node.

DATA INITIALISATION
-------------------
Every entry is generated by a formula (no file I/O needed):

    A(i, j) = ((2i + j) mod 7) - 3
    B(i, j) = ((i + 3j) mod 5) - 1       for 0 <= i, j < N

All entries of C come out as small whole numbers, so every correct
implementation prints exactly the same values regardless of how many
processes or threads are used.

HOW THE WORK IS DIVIDED
------------------------
With p MPI processes, the rows of A, B and C are split into p blocks.
Process r owns block r of each matrix. If p does not divide N evenly,
the first (N mod p) processes get one extra row.

To compute its rows of C, process r needs:
- Its own rows of A                   (already has them)
- ALL rows of B                       (must get them somehow)

This "getting all of B" is solved three different ways in the four tasks.


THE FOUR TASKS
==============

Task 1.1 — Serial + OpenMP (single machine, multiple threads)
--------------------------------------------------------------
Write matrix multiply two ways and compare:

  i-j-k order (naive):
      for i: for j: for k:
          C[i][j] += A[i][k] * B[k][j]
  Inner loop steps down a COLUMN of B -> jumps N doubles in memory
  each step -> cache misses -> slow.

  i-k-j order (cache-friendly):
      for i: for k: for j:
          C[i][j] += A[i][k] * B[k][j]
  Inner loop streams along a ROW of B and a ROW of C, both contiguous
  in memory -> cache-friendly -> faster.

Then parallelise the i-k-j version with OpenMP:

      #pragma omp parallel for
      for i: ...

  Thread t owns a subset of rows i. Each element of C belongs to exactly
  one row, so only one thread ever writes it -> no race condition.

Benchmarks: N = 1000 and 2000, with 1, 2, 4, ... threads up to core count.


Task 1.2 — Version A: MPI Broadcast (collective communication)
--------------------------------------------------------------
Rank 0 builds the full A and B, then:
  1. MPI_Scatterv  — send each process its rows of A
  2. MPI_Bcast     — send the ENTIRE B to every process
  3. Each process multiplies its rows of A x full B
  4. MPI_Gatherv   — collect all rows of C back to rank 0

Problem: every process stores all of B.
  For N = 32768 with p = 8: each of the 8 nodes stores 8 GiB for B.
  That is 8 x 8 = 64 GiB just for copies of B -> does not scale.

Benchmarks: N = 2000 and 4000, p = 1, 2, 4, 8. Time each of the 4 steps.


Task 1.3 — Version B: Blocking Ring
------------------------------------
Each process creates only its own rows of A and B. They pass B blocks
around a ring so every process eventually multiplies against every block:

  Step s (s = 0 ... p-1):
    - Process r holds block B_q   where q = (r + s) mod p
    - Computes: C_r += A_r[:,columns of block q] x B_q
    - Sends B_q  to left  neighbour (r-1+p) mod p   (MPI_Send)
    - Receives next block from right neighbour (r+1) mod p   (MPI_Recv)

After p steps, every process has used every block of B.
Memory per process: only 2 blocks of B (current + one being received).

Deadlock risk: if ALL processes call MPI_Send first, large messages block
waiting for a receiver that never comes. Fix: even ranks send first, odd
ranks receive first.

Benchmarks: compare Version A and B in time and memory for N = 2000, 4000.


Task 1.4 — Version C: Non-blocking Ring + OpenMP
-------------------------------------------------
Same ring as Version B but uses non-blocking messages so communication
and computation overlap:

  For each step s:
    1. MPI_Irecv  — start receiving the NEXT B block (into buffer 1)
    2. MPI_Isend  — start sending the CURRENT B block (from buffer 0)
    3. Multiply using the current B block while messages travel (OpenMP)
    4. MPI_Waitall — wait for both messages to finish
    5. Swap buffers (0 <-> 1) and repeat

Two buffers are needed: one being computed with, one being filled by the
network. A buffer must NOT be read or written while its message is still
in progress (MPI owns it until Waitall returns).

Also run in hybrid mode: fewer MPI processes, more OpenMP threads each,
and compare against one process per core.

Benchmarks: measure time spent multiplying vs. waiting for each step.


CORRECTNESS CHECKS
==================
Small test (N = 8) — full matrix must match exactly:

      col  0    1    2    3    4    5    6    7
  row 0:   0    6   -8   -2  -11    0    6   -8
  row 1:  17  -11    1   -2  -10   17  -11    1
  row 2:  -8    0    3   -9   19   -8    0    3
  row 3:  -5    4   -2   12    6   -5    4   -2
  row 4:   5   -6   -7   12  -14    5   -6   -7
  row 5:   1   -9   16   -9    1    1   -9   16
  row 6: -10   16   -3   -2    9  -10   16   -3
  row 7:   0    6   -8   -2  -11    0    6   -8

Large runs — five specific entries must match:

  N     C(0,0)  C(0,1)  C(1,0)  C(N/2,N/2)  C(N-1,N-1)
  1000      2      -2       7           3           9
  2000      5     -10      15         -12          -5
  4000     -7       5      20           9          17


HOW TO RUN
==========
  make                                      # build

  mpirun -n 1 ./task1 8                     # N=8 correctness check
  OMP_NUM_THREADS=4 mpirun -n 1 ./task1 1000   # Task 1.1, 4 threads
  mpirun -n 4 ./task1 2000                  # Tasks 1.2 / 1.3 / 1.4
