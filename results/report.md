### 2.2 Task 1.1 — Loop order and OpenMP

| 2000 | 2 | 31.26 | 3.78 | 4.44 | 8.3× | 0.85 |
| 2000 | 4 | 30.96 | 3.84 | 4.56 | 8.1× | 0.84 |
| 4000 | 1 | 480.36 | 32.87 | 35.86 | 14.6× | 0.92 |

**Why i-k-j is faster.**
- In i-j-k the innermost loop runs over k and reads `B[k*N + j]`. That is a walk down a column of B with a stride of N doubles (16–32 KB). Every access touches a new cache line and soon a new page. For N ≥ 2000, one column of B no longer stays in cache between consecutive j.
- In i-k-j, `a = A[i][k]` is held in a register. The innermost loop runs over j and streams through row k of B and row i of C, both contiguous. Every cache line that is loaded is used completely (8 doubles), the hardware prefetcher works, and the compiler can vectorise the loop.
- The gap grows with N: 4.6× at N = 1000, 7.9× at N = 2000, 14.6× at N = 4000. The working set of the strided column walk exceeds each cache level in turn.

**Why no two threads write the same element of C.**
- `#pragma omp parallel for` is placed on the outer loop over i (rows of C). Each iteration i is executed by exactly one thread.
- That thread is the only one that writes `C[i][0..N−1]`. The other loop variables (k, j, `a_ik`) are declared inside the loop, so they are private.
- A and B are only read. There is therefore no data race and no reduction or atomic is needed.

**Threads on this cluster.**
- The node has one core, so 2 and 4 threads time-share it. They give no speedup: 4.26 s → 4.44 s → 4.56 s at N = 2000.
- The OpenMP version with one thread is slightly slower than the plain serial i-k-j (≈10 % at N ≥ 2000; more at N = 1000, where the run is short and fixed overheads matter). The likely cause is the outlined parallel region and per-row zeroing, which give the compiler less freedom to optimise than the serial function with `memset`.
- On a multi-core node the same code would scale with the number of cores, because the rows are independent.

### 2.4 Task 1.3 — Version B (ring with blocking messages)

Each process creates only its own rows of A and its own block B_r. In step s it:
- multiplies with the block of owner q = (r + s) mod p,
- sends that block to its left neighbour (r − 1 + p) mod p,
- receives the next block from its right neighbour (r + 1) mod p.

**Even/odd ordering.** Even ranks call `MPI_Send` first and then `MPI_Recv`; odd ranks do the opposite. Blocks have different sizes when p does not divide N, so each receive uses the size of the block's owner. The ring was tested with p = 1, 2, 3, 8; p = 3 is odd and does not divide 8, 1000 or 2000.

**Why the program could hang if every process called MPI_Send first.**
- For large messages (here 2–30 MB per block), `MPI_Send` uses the rendezvous protocol. It does not return until the matching receive has been posted, because the message cannot be buffered.
- If all p processes call `MPI_Send` at the same time, each one waits for its left neighbour to post `MPI_Recv`. But that neighbour is itself stuck in its own `MPI_Send`. This is a circular wait, i.e. deadlock.
- Small messages may still work through MPI's eager buffering, which makes the bug appear only for large N.
- With even/odd ordering, every even sender faces an odd receiver, so the chain is broken.
- For odd p, the two even neighbours 0 and p−1 meet. Rank p−1 sends to rank p−2 (odd), which receives first, so p−1 completes its send, then receives, and rank 0's send completes too. No cycle remains.

- Each step sends only N²/p doubles to one neighbour, instead of the root sending N² doubles to everyone.

### 2.5 Task 1.4 — Version C (non-blocking ring + OpenMP)

In every step, Version C:
1. calls `MPI_Irecv` for the next block into `Bbuf[1−cur]`,
2. calls `MPI_Isend` for the current block from `Bbuf[cur]`,
3. multiplies with `Bbuf[cur]` using `#pragma omp parallel for` (MPI is called only outside the parallel region),
4. calls `MPI_Waitall`,
5. swaps the two buffers.

**Why a buffer must not be changed or read while its message is in progress.**
- After `MPI_Isend`/`MPI_Irecv` returns, MPI owns the buffer until the request completes.
- For the send buffer, MPI may still be copying it to the network (or may be doing a zero-copy transfer). Overwriting `Bbuf[cur]` before `MPI_Waitall` could send corrupted data.
- For the receive buffer, the data arrives at an unspecified time and possibly in pieces. Reading `Bbuf[1−cur]` before the wait could use half-old, half-new values.
- This is why two buffers are needed. We compute only with `Bbuf[cur]`, which is only read while it is being sent; reading is safe.
- We touch `Bbuf[1−cur]` only after `MPI_Waitall` says the receive is complete.

**Note on the implementation.**
- The code selects `omp_set_schedule(omp_sched_static, 1)`, i.e. static with chunk size 1. Rows are dealt round-robin, so every thread gets an equal share of the popular users; this is why the measured link counts are equal.
- The plain `schedule(static)` asked for in the task gives each thread one contiguous block of n/t rows. The "contiguous blocks" rows show what that does.
  - Those link counts are taken from the equal-rows MPI blocks of Tasks 2.2/2.4, which are exactly the same row ranges.
  - Thread 0 gets all users < n/10 that are popular (64–127 links), so it handles 4.16 M links while the others handle 2.0 M. That is 1.64× the average for 4 threads.
- To reproduce this inside Task 2.1, change the chunk argument in `csr_rows` from 1 to 0 (the default block schedule).

**Explanation of static vs dynamic.**
- Work per row is proportional to its number of links, and all heavy rows sit in the first 10 % of the rows.
- With contiguous static blocks, the thread owning the first block does 1.2–1.6× the average work and all others wait for it at the implicit barrier.
- `schedule(dynamic, 64)` hands out chunks of 64 rows on demand. A thread that drew heavy rows simply takes fewer chunks: link imbalance 1.014 for 2 threads, 1.050 for 4, and the busy times of the 4 threads differ by under 0.4 %.
- On this one-core node there is a second effect.
  - With static scheduling and more threads than cores, the 2–4 threads time-share the core. Each one's fixed share of rows is interleaved through context switches, with poor cache reuse (thread busy time 0.18 s per step for 4 threads vs 0.07 s with dynamic). The static runs get slower: 0.83 → 1.30 → 1.98 s.
  - With dynamic scheduling, whichever thread is currently running keeps taking chunks, so the time stays at 0.84–0.85 s.

- Version B receives 3,400× less data (32 KiB vs 107 MiB at p = 8) and is 9–44× faster than Version A for p ≥ 2.

**Waiting in MPI_Waitall: interior-before-Waitall vs all-after-Waitall.**
- At p = 2 the overlap version waits 0.0095 s, against 0.0612 s without overlap (6.4× less). The 32 KiB halo messages are in flight while the ≈250,000 interior rows are computed, so by the time `MPI_Waitall` is called the halos have arrived.
- Without overlap, the process posts the messages and immediately waits for the full network round trip, which is only then followed by the computation.
- At p = 4 and 8 the wait is about 0.25 s in both variants. There the wait is not transfer time: it is waiting for the neighbour, which is slower for two reasons.
  - It shares a core with 1–2 other ranks.
  - Or it owns the popular users (equal-rows rank 0 has 2–3× the links of the others).
- Overlap can hide message latency, but it cannot hide a slower partner. The total time therefore barely changes (0.600 vs 0.594 s at p = 4, 0.663 vs 0.690 s at p = 8).

### 3.5 Task 2.4 — Load balancing (equal rows vs equal links) and hybrid

**How the balanced boundaries are computed.**
- Rank 0 computes the total number of links T with `degree()`.
- It then walks over the users with a running sum and cuts boundary r at the first user where `sum·p ≥ T·r`.
- Two passes then enforce at least 128 rows per block, because the halo needs that:
  - a forward pass sets `b[q] ≥ b[q−1]+128`,
  - a backward pass sets `b[q] ≤ b[q+1]−128`.
- Rank 0 sends the boundaries to all processes with `MPI_Bcast`.
- After the run, the computation time of every process is collected with `MPI_Gather`.

- **Cost per link is not constant.**
  - Rank 0 with equal rows handles 1.8× more links than ranks 1 and 2, yet computes only 5–14 % longer.
  - A popular user's 64–127 links all point within ±128 positions, so they read the same few cache lines of H again and again. ## 4. Question 3 — Adding up partial results in parallel training

### 4.1 Implementation and correctness

- Every process creates only its own examples, a block of the 512 examples (the first 512 mod p processes get one more). It does this for each of the L = 8 layers and S = 5 steps:
  1. computes G_l = X_l × E_l with the OpenMP i-k-j multiplication from Q1,
  2. copies the 8 gradients into one array of 8m² doubles,
  3. all-reduces that array,
  4. updates W_l ← W_l − G_l / 65536.
- **Three all-reduces were implemented.**
  - (a) `MPI_Reduce` to rank 0 (`MPI_IN_PLACE`) followed by `MPI_Bcast`.
  - (b) one `MPI_Allreduce` (`MPI_IN_PLACE`).
  - (c) our own `ring_allreduce(double *v, long n, MPI_Comm comm)`.
- **How `ring_allreduce` works.**
  - The array is cut into p chunks; the first n mod p chunks get one extra element, so any n works.
  - Phase 1 (add) has p − 1 steps. Process r sends chunk (r − s) mod p to the right, receives chunk (r − s − 1) mod p from the left into a temporary buffer, and adds it to its own copy. After this, rank r owns the full sum of chunk (r + 1) mod p.
  - Phase 2 (share) has p − 1 steps. Process r sends chunk (r + 1 − s) mod p and receives chunk (r − s) mod p, which overwrites its copy.
  - Every step uses `MPI_Irecv` + `MPI_Isend` + `MPI_Waitall`. Phase 2 uses tags p + s so that its messages cannot match those of phase 1.
- **Correctness (m = 512).** All three versions were run with p = 1, 2, 3, 4, and the ring also with p = 8.
  - Rank 0 printed Table 4(a) exactly: G0(1,2) = 33, G0(511,511) = 24, G7(511,511) = 27.
  - **Every rank** printed exactly the Table 4(b) weights: W0(0,0) = 0.0001220703125, W0(1,2) = −0.000152587890625, W7(511,511) = −0.00079345703125.
  - All copies of the weights are therefore identical after the all-reduce, for p that does and does not divide 512 (p = 3).

**Why the ring is slow for small data and good for large data.**
- A ring all-reduce needs 2(p − 1) messages in sequence, each paying the full network latency α (here ≈0.5 ms per ring step on the virtual TCP network: 1.03 ms / 2 steps at p = 2, 3.25 ms / 6 steps at p = 4). For 1 KB the data term is negligible, so the time is ≈ 2(p−1)·α:
  - p = 2: 1.03 ms vs 0.53 ms for Reduce + Bcast.
  - p = 4: 3.25 ms vs 1.25 ms.
  - Tree-based collectives need only ≈ 2·log₂p latencies.
- For large data the latency is irrelevant and the bandwidth term dominates. In the ring, each process sends and receives 2(p − 1)/p · n doubles, less than 2n for any p, and all links are busy at the same time. With Reduce + Bcast, rank 0 must receive and send ≈ n · log₂p doubles through one network link and does all the additions.
- Measured: at p = 4 the ring is the fastest method for 1 MB (0.0225 s) and 64 MB (0.886 s). That is 1.8× faster than Reduce + Bcast and 4.8× faster than this cluster's `MPI_Allreduce` at 64 MB. Its 64 MB time grew only from 0.56 s (p = 2) to 0.89 s (p = 4), in line with the 2(p−1)/p factor (1.0 → 1.5).

**Why adding processes stops helping.**
- With the batch fixed at 512 examples, each process computes 512/p examples. The compute time per step falls from 0.418 s (p = 1) to 0.152 s (p = 3), close to 1/p.
- It does not fall further for p > 3, because there are only 3 cores.
- The all-reduce, however, always works on the full gradient of 8 · m² doubles: 16 MiB for m = 512, 64 MiB for m = 1024. This does not shrink with p.
  - With the ring, each process sends 2(p−1)/p of it, which *grows* towards 2× the gradient.
  - With Reduce + Bcast the root's traffic grows with log₂p.
- The all-reduce time therefore rises (0.20 → 0.37 → 0.92 s per step) while the compute falls. From p = 3 on it is the majority of the step (57 % → 85 %).
- This is Amdahl's law with a communication part that grows instead of staying constant. The best p is where the drop in compute equals the rise in all-reduce time: p = 3 here.
- For m = 1024 the compute and the gradient are both 4× larger. The balance point would be similar, but every all-reduce would move 64 MiB. The benchmark measured 0.56–0.89 s for one 64 MiB ring all-reduce at p = 2–4 and up to 37.8 s for `MPI_Allreduce` at p = 8.

- The library `MPI_Allreduce` was the worst choice on this virtual cluster for p ≥ 3.

## 5. Overall comparison and conclusions

| question | sequential | best OpenMP-only (1 node) | best MPI-only | best hybrid / one process per node | fastest |
|---|---|---|---|---|---|
| Q1, N = 4000 (s) | 32.87 (i-k-j) | 35.86 (1 thread) | 27.00 (B, 8 × 1) | 25.80 (C, 3 × 1) | Version C, 1 proc/node — 1.27× |
| Q2, n = 10⁶ (s) | 1.062 | 0.840 (dynamic, 2 thr.) | 0.525 (B balanced, 4 × 1) | 0.482 (B, 3 × 1) | Version B, 1 proc/node — 2.20× |
| Q3, m = 512 (s) | 2.148 (p = 1) | — | 1.883 (ring, 3 × 1) | 1.883 (ring, 3 × 1) | ring all-reduce, 3 × 1 — 1.14× |

**Findings.**
1. **Data movement decides the winner.**
   - The versions that send the least data are the fastest in every question: the ring for dense blocks, halo exchange for the sparse matrix, the ring all-reduce for gradients.
   - The versions that replicate everything (Version A of Q1 and Q2, Reduce + Bcast) are limited by the root or by the network. They do not scale even when compute shrinks.
2. **Memory scalability.** Only the ring (Q1 B/C) and halo (Q2 B) versions divide all memory by p. Q1 Version A needs 8N² bytes per node and could not run at N = 32768 on any number of nodes.
3. **Load balance must be measured, not assumed.**
   - Hubs make equal-row blocks 1.6× unbalanced in links.
   - But link count is not the full cost: the cost is ≈ rows + links, and over-balancing by links made rank 0 wait at p = 3.
   - On this cluster, the number of ranks sharing a core was the dominant imbalance for p > 3.
4. **Overlap helps only when there is something to hide.** It cut the halo wait by 6.4× at p = 2. It could not hide waiting for slower neighbours, and with one core per VM the non-blocking transfers progress mostly inside `MPI_Waitall`.
5. **Limits of this cluster.**
   - 3 single-core VMs mean that OpenMP threads and more than 3 processes cannot add compute. The maximum achievable speedup is 3.
   - We reached 1.27× (Q1), 2.20× (Q2) and 1.14× (Q3).
   - The dense and training codes are compute-bound per VM but slowed down when all VMs ran together. The likely cause is that they share the physical host, which we did not verify.
   - All times are single runs.
